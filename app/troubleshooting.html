🔥 Linux Production Troubleshooting

Diagnose real server failures using a safe, evidence-first and layer-by-layer workflow.

⚡ 60-Second Troubleshooting Method

  1. Confirm the exact symptom and affected users.
  2. Record when the issue started.
  3. Check recent deployments and configuration changes.
  4. Measure before restarting or changing anything.
  5. Move through CPU, memory, disk, network and application layers.
  6. Compare working and failing systems or requests.
  7. Apply the smallest reversible fix.
  8. Verify service health from the user’s perspective.
  9. Document the root cause and prevention action.
Restarting immediately may temporarily restore service but can destroy useful evidence. Capture status, logs and metrics first.

1. First Five-Minute Server Check

date
hostnamectl
uptime
who
w

systemctl --failed
journalctl -p warning --since "30 minutes ago"

free -h
df -hT
df -i

top
ps aux --sort=-%cpu | head
ps aux --sort=-%mem | head

ip -br address
ip route
ss -s
sudo ss -lntup

Always capture the exact time:

date --iso-8601=seconds
timedatectl
Accurate time is essential when correlating application, kernel, database, proxy and monitoring logs.

2. Server Unreachable

Diagnostic order

  1. Confirm hostname and IP address.
  2. Check monitoring or cloud-instance state.
  3. Test network reachability.
  4. Check the required port.
  5. Check host and external firewall rules.
  6. Use console access if SSH is unavailable.

From the client

getent ahosts SERVER_NAME
ping -c 4 SERVER_IP
tracepath SERVER_IP
nc -vz SERVER_IP PORT
curl -v --connect-timeout 5 \
  http://SERVER_IP:PORT

From the server console

ip -br address
ip route
ip neigh
sudo ss -lntup
systemctl --failed
sudo nft list ruleset
Symptom Likely direction
Connection refused Host reachable, but service not listening or actively rejecting
Connection timeout Routing, firewall, security group or packet loss
No route to host Missing route, gateway, interface or firewall rejection

3. High CPU Usage

uptime
top
mpstat -P ALL 1 5
pidstat -u 1 5

ps -eo pid,ppid,user,stat,pcpu,pmem,comm \
  --sort=-pcpu | head -20

Inspect threads of a process:

top -H -p PID

ps -L -p PID \
  -o pid,tid,psr,stat,pcpu,comm \
  --sort=-pcpu

Check whether CPU time is user, system, I/O wait or steal:

vmstat 1 5
mpstat 1 5
  • us: application code
  • sy: kernel activity
  • wa: waiting for I/O
  • st: hypervisor stole CPU time

Optional deeper profiling:

sudo perf top
sudo strace -c -p PID
Do not kill the highest-CPU process until you know its role, dependencies and impact.

4. High Load Average

Load average counts runnable tasks and tasks in uninterruptible sleep. High load does not always mean high CPU usage. 

uptime
cat /proc/loadavg
nproc
vmstat 1 5

ps -eo state,pid,ppid,wchan:32,comm \
  | awk '$1 ~ /D|R/'

Check storage pressure:

iostat -xz 1 5
pidstat -d 1 5
sudo dmesg -T | tail -100
CPU usage Load Likely direction
High High CPU-bound workload
Low High I/O wait, blocked storage or network filesystem
High steal High Virtualization host contention

5. Memory Exhaustion

free -h
cat /proc/meminfo
vmstat 1 5

ps -eo pid,user,rss,vsz,pmem,comm \
  --sort=-rss | head -20

Inspect a specific process:

cat /proc/PID/status
cat /proc/PID/smaps_rollup
pmap -x PID | tail -20

Check swap activity:

swapon --show
cat /proc/swaps
vmstat 1 10
Low “free” memory is not automatically a problem. Linux uses otherwise unused RAM for cache. Check available, swap activity, reclaim pressure and application behaviour.

6. OOM Kills

Search kernel logs:

sudo journalctl -k \
  | grep -Ei 'oom|out of memory|killed process'

sudo dmesg -T \
  | grep -Ei 'oom|out of memory|killed process'

Inspect the process or service:

systemctl show SERVICE_NAME \
  -p MemoryCurrent \
  -p MemoryMax \
  -p MemoryHigh \
  -p OOMPolicy \
  -p OOMScoreAdjust

cat /proc/PID/oom_score
cat /proc/PID/oom_score_adj
cat /proc/PID/cgroup

For the relevant cgroup v2 directory:

cat memory.current
cat memory.max
cat memory.events
cat memory.stat
  1. Confirm whether it was system-wide or cgroup OOM.
  2. Identify the killed process.
  3. Compare usage with the configured limit.
  4. Check for leaks, traffic spikes and oversized caches.
  5. Right-size the application and limit after measurement.

7. Disk Full

df -hT
findmnt
lsblk -f

sudo du -xhd1 / 2>/dev/null \
  | sort -h

sudo du -xhd1 /var 2>/dev/null \
  | sort -h

Find large files without crossing filesystems:

sudo find /var \
  -xdev \
  -type f \
  -size +500M \
  -printf '%s %p\n' 2>/dev/null \
  | sort -n

Check journal usage:

journalctl --disk-usage
sudo du -sh /var/log/* 2>/dev/null
Do not blindly delete logs, database files or application data. Identify ownership, retention policy and recovery impact first.

8. Inode Exhaustion

A filesystem can have free storage space but still reject new files when all inodes are used. 

df -i
df -hT

sudo du --inodes -x -d1 /var \
  2>/dev/null | sort -n

Count files in a suspected directory:

sudo find /suspected/path \
  -xdev \
  -type f \
  -printf '.' 2>/dev/null \
  | wc -c

Common causes:

  • Session files
  • Mail queues
  • Application cache files
  • Unrotated small logs
  • Temporary files
  • Container storage layers

9. Filesystem Mount Failure

lsblk -f
sudo blkid
findmnt
findmnt --verify
cat /etc/fstab

systemctl --failed \
  --type=mount

sudo journalctl -b \
  | grep -Ei 'mount|filesystem|fsck'

sudo dmesg -T \
  | grep -Ei 'I/O error|filesystem|ext4|xfs'

Check a specific mount unit:

systemctl status \
  path-to-mount.mount

journalctl -u \
  path-to-mount.mount

Verify:

  • Correct UUID or device
  • Correct filesystem type
  • Mount-point directory exists
  • Storage device is visible
  • Network storage is reachable
  • Filesystem is not corrupted
Never run filesystem repair against a mounted production filesystem. Confirm backups and follow the filesystem-specific recovery procedure.

10. Service Down

systemctl status SERVICE_NAME \
  --no-pager -l

systemctl is-active SERVICE_NAME
systemctl is-enabled SERVICE_NAME
systemctl --failed

journalctl -u SERVICE_NAME \
  --since "30 minutes ago"

systemctl show SERVICE_NAME \
  -p Result \
  -p ExecMainStatus \
  -p ExecMainCode \
  -p MainPID

Inspect the complete unit:

systemctl cat SERVICE_NAME
systemctl show SERVICE_NAME
systemctl list-dependencies SERVICE_NAME

Validate the application configuration before restarting:

APPLICATION_BINARY --test-config
The exact configuration-test command depends on the application. Examples include nginx -t and sshd -t.

11. Port Unavailable

sudo ss -lntup
sudo ss -ltnp 'sport = :PORT'
sudo lsof -i :PORT
sudo fuser -v PORT/tcp

curl -v http://127.0.0.1:PORT
nc -vz 127.0.0.1 PORT

Verify the listening address:

  • 127.0.0.1:PORT — accessible locally only
  • 0.0.0.0:PORT — listening on all IPv4 addresses
  • [::]:PORT — listening on IPv6 and possibly IPv4

Check firewall:

sudo nft list ruleset
sudo ufw status verbose
sudo firewall-cmd --list-all
  1. Confirm the process is running.
  2. Confirm the port is listening.
  3. Test locally.
  4. Test from the same network.
  5. Check host and external firewalls.
  6. Check proxy and load-balancer health.

12. DNS Failure

cat /etc/resolv.conf
grep '^hosts:' /etc/nsswitch.conf

getent ahosts example.com
resolvectl status
resolvectl query example.com

dig example.com
dig @DNS_SERVER example.com
dig +trace example.com

Separate DNS from network failure:

ping -c 3 IP_ADDRESS
curl -v http://IP_ADDRESS
getent hosts example.com
Test result Direction
IP works, name fails Resolver, DNS server, search domain or DNS record
IP and name both fail General network, routing or firewall issue
One resolver works Configured DNS server problem

13. Network Connectivity Failure

ip -br link
ip -br address
ip route
ip rule
ip neigh

ping -c 4 DEFAULT_GATEWAY
tracepath DESTINATION_IP
ss -s

sudo ethtool INTERFACE
sudo journalctl -k \
  | grep -Ei 'link|network|firmware|nic'

Check route selection:

ip route get DESTINATION_IP

Check NetworkManager when used:

nmcli device status
nmcli connection show
journalctl -u NetworkManager \
  --since "30 minutes ago"

Troubleshoot layer by layer:

  1. Interface link
  2. IP address and subnet
  3. Default or specific route
  4. Neighbour resolution
  5. Firewall
  6. DNS
  7. Application port

14. SSH Failure

From the client

ssh -vvv USER@SERVER
nc -vz SERVER 22
getent ahosts SERVER

From server console

sudo sshd -t
sudo sshd -T
sudo ss -ltnp | grep ':22'

sudo systemctl status ssh sshd
sudo journalctl \
  -u ssh \
  -u sshd \
  --since "30 minutes ago"

Check the user and key path:

getent passwd USERNAME
passwd -S USERNAME
namei -l \
  /home/USERNAME/.ssh/authorized_keys

ls -ld /home/USERNAME/.ssh
ls -l \
  /home/USERNAME/.ssh/authorized_keys

Also verify:

  • Firewall and cloud security rules
  • Correct username and key
  • Account is not locked or expired
  • AllowUsers and AllowGroups rules
  • SELinux or AppArmor denials
  • Filesystem has free space and inodes
Keep the existing administrator session open while testing SSH changes from a second terminal.
15. Permission Denied 
id
id USERNAME

ls -ld /path
namei -l /path/to/file
stat /path/to/file
getfacl /path/to/file

findmnt -T /path/to/file \
  -o TARGET,SOURCE,FSTYPE,OPTIONS

Check mandatory access controls:

ls -lZ /path/to/file
getenforce
sudo ausearch -m AVC -ts recent

sudo aa-status
sudo journalctl -k \
  | grep -i apparmor

Possible causes:

  • Owner or group mismatch
  • Missing directory execute permission
  • ACL override
  • SELinux context or policy denial
  • AppArmor profile denial
  • Read-only or noexec mount
  • Service running as a different account
Avoid using chmod 777 as a troubleshooting fix. Identify the exact required access and grant the minimum permission.

16. Package Installation Failure

Debian and Ubuntu investigation

sudo apt update
apt-cache policy PACKAGE_NAME
dpkg --audit
sudo apt-get check

ps aux \
  | grep -E 'apt|dpkg' \
  | grep -v grep

df -h
df -i

After confirming no package manager is running:

sudo dpkg --configure -a
sudo apt --fix-broken install

RHEL-family investigation

sudo dnf repolist
sudo dnf check
sudo dnf list PACKAGE_NAME
sudo dnf history
sudo rpm -Va

Check repository and network access:

getent hosts REPOSITORY_HOST
curl -I REPOSITORY_URL
timedatectl
Never delete package-manager lock files just because an error mentions a lock. First verify whether another package operation is genuinely running.

17. Boot Failure

When the system boots into rescue or emergency mode:

systemctl --failed
systemctl status
journalctl -xb
journalctl -p err -b
journalctl -k -b

lsblk -f
findmnt
findmnt --verify
cat /etc/fstab

Inspect the previous boot:

journalctl --list-boots
journalctl -b -1 -p warning
journalctl -k -b -1

Analyze boot time:

systemd-analyze
systemd-analyze blame
systemd-analyze critical-chain

Common causes:

  • Invalid /etc/fstab entry
  • Missing storage device
  • Filesystem corruption
  • Broken initramfs
  • Kernel or driver problem
  • Failed required service
  • Incorrect bootloader configuration
Bootloader, initramfs and filesystem recovery commands are distribution-specific. Confirm the exact system and preserve recovery access before changing them.

18. Slow Application

Measure every layer:

  1. Client and DNS time
  2. Network connection time
  3. Proxy or load balancer
  4. Application processing
  5. Database or external dependency
  6. CPU, memory and storage
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup}
connect=%{time_connect}
tls=%{time_appconnect}
first_byte=%{time_starttransfer}
total=%{time_total}\n' \
  https://APPLICATION_URL

Inspect the server:

uptime
vmstat 1 5
iostat -xz 1 5
pidstat -u -r -d 1 5
ss -s

systemctl status SERVICE_NAME
journalctl -u SERVICE_NAME \
  --since "30 minutes ago"

Optional deeper inspection:

sudo strace -c -p PID
sudo perf top -p PID
sudo lsof -p PID

19. Log Investigation

journalctl --list-boots
journalctl -b
journalctl -b -1
journalctl -k
journalctl -p warning

journalctl \
  --since "2026-08-26 10:00:00" \
  --until "2026-08-26 10:15:00"

journalctl -u SERVICE_NAME
journalctl _PID=PID
journalctl -f

Useful options:

journalctl --no-pager
journalctl -n 100
journalctl -o short-iso
journalctl -o verbose
journalctl --disk-usage

Traditional logs may exist under:

/var/log/syslog
/var/log/messages
/var/log/auth.log
/var/log/secure
/var/log/kern.log
/var/log/audit/audit.log

Investigation approach

  1. Define the exact time window.
  2. Start with application and service logs.
  3. Correlate proxy, database and kernel logs.
  4. Search by request ID, user, PID, IP or error code.
  5. Compare with deployment and monitoring events.

20. Deleted-Open-File Disk Issue

A process can keep disk blocks allocated after a file has been deleted. This can make df show high usage while du cannot find the data. 

df -h
sudo du -xsh /
sudo lsof +L1

Inspect a specific process:

sudo ls -l /proc/PID/fd
sudo lsof -p PID | grep deleted

Safe resolution flow

  1. Identify the process and deleted descriptor.
  2. Confirm whether it is a service, database or critical workload.
  3. Preserve needed data or logs.
  4. Gracefully restart or reload the owning process.
  5. Confirm space is released with df -h.
  6. Fix log rotation or application behaviour.
Do not terminate an important database or production process without understanding its recovery behaviour.

21. Environment Variable Issues

Inspect the current shell:

env | sort
printenv VARIABLE_NAME
echo "$PATH"
type -a COMMAND_NAME
command -v COMMAND_NAME

Inspect a running process carefully:

sudo tr '\0' '\n' \
  < /proc/PID/environ

Inspect a systemd service:

systemctl cat SERVICE_NAME

systemctl show SERVICE_NAME \
  -p User \
  -p Group \
  -p Environment \
  -p EnvironmentFiles \
  -p WorkingDirectory \
  -p ExecStart

Common causes:

  • Variable set in a shell profile but not in systemd
  • Different PATH for interactive and service accounts
  • Missing EnvironmentFile
  • Incorrect quoting
  • Service not restarted after configuration change
  • Secret injected into the wrong environment
Process environments may contain credentials and tokens. Never paste complete environment output into public logs or chat.

🎯 Interview Questions

What is your first troubleshooting step?

Confirm the exact symptom, scope and start time, then collect evidence before changing the system.

High load but low CPU—what could cause it?

Processes may be blocked in uninterruptible sleep, commonly due to storage, device or network-filesystem I/O.

Why can df and du show different usage?

Deleted files may still be held open by processes, files may be hidden beneath mount points, or the commands may be measuring different filesystem boundaries.

Connection refused vs timeout?

Refused usually means the host responded but the port was not accepting connections. Timeout commonly indicates dropped traffic, routing failure or an unreachable host.

How do you confirm an OOM kill?

Inspect kernel logs and cgroup memory events, identify the killed process and compare usage against system or service limits.

Why might an application work manually but fail in systemd?

systemd can use a different user, working directory, environment, PATH, resource limit or security sandbox.

Why avoid chmod 777?

It grants excessive access and can hide the real ownership, ACL, SELinux, AppArmor or mount problem.

Why collect logs before restarting?

Restarting can clear process state, rotate logs and remove evidence needed to identify the root cause.

✅ Production Troubleshooting Checklist

  • Confirm the exact symptom.
  • Record the time and affected scope.
  • Check recent changes.
  • Capture metrics and logs before restarting.
  • Check CPU, memory, disk, network and application layers.
  • Distinguish symptoms from root causes.
  • Use the smallest reversible fix.
  • Validate from the end-user perspective.
  • Monitor after recovery.
  • Document root cause and prevention work.
