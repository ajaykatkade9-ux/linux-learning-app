🔑 SSH & Remote Administration

Secure Shell, authentication, SSH keys, remote administration, file transfer, troubleshooting and production security practices.

    ↓
SSH Server
    ↓

Remote Shell / Command

Default SSH port:

22/tcp

1. SSH Basics

SSH provides encrypted communication between systems.

Basic connection: 
ssh USER@SERVER
Custom port: 
ssh -p PORT USER@SERVER
Run one remote command: 
ssh USER@SERVER "hostname"

2. SSH Client and Server

The local machine normally runs the SSH client. The remote machine runs an SSH server such as OpenSSH sshd.

Check client: 
ssh -V
Check server where applicable: 
systemctl status ssh

systemctl status sshd

Service naming depends on the distribution.

3. Password Authentication

SSH can authenticate users with passwords when the server permits it. 

ssh USER@SERVER

For production systems, key-based authentication is commonly preferred because it supports stronger operational practices.

4. Public-Key Authentication

SSH key authentication normally uses a key pair:

  • Private key — stays with the client and must be protected
  • Public key — can be installed on the remote account
Concept: 
Private Key
   ↓
Client proves identity
   ↓
Server checks authorized public key
   ↓
Authentication succeeds

5. Generate an SSH Key

For a personal lab key:

ssh-keygen -t ed25519

Inspect:

ls -la ~/.ssh

Never publish or casually copy your private key.

6. authorized_keys

Public keys allowed to authenticate to an account are commonly stored in: 

~/.ssh/authorized_keys
Inspect permissions: 
ls -ld ~/.ssh

ls -l ~/.ssh/authorized_keys

Incorrect ownership or permissions can cause key authentication failures.

7. Install a Public Key

Where available:

ssh-copy-id USER@SERVER

This installs your public key into the remote user's authorized_keys configuration.

8. known_hosts

SSH records identities of remote hosts in: 

~/.ssh/known_hosts

This helps detect cases where the identity presented by a server unexpectedly changes.

Inspect: 
ls -l ~/.ssh/known_hosts

9. SSH Client Configuration

Client settings can be placed in:

~/.ssh/config
Example: 
Host dev-server
    HostName 10.0.0.20
    User devops
    Port 22
Then connect using: 
ssh dev-server

10. SSH Server Configuration

A common server configuration file is: 

/etc/ssh/sshd_config
Inspect without changing anything: 
grep -v '^#' /etc/ssh/sshd_config | grep -v '^$'

Exact configuration and included files can vary by distribution.

11. Test SSH Configuration

Before applying server-side SSH configuration changes, validate configuration where supported: 

sshd -t

Invalid SSH configuration can lock administrators out of remote systems, so production changes should be handled carefully.

12. SSH Permissions

Common secure permission patterns often include: 

chmod 700 ~/.ssh

chmod 600 ~/.ssh/authorized_keys

Check ownership too:

ls -ld ~/.ssh

ls -l ~/.ssh

Do not blindly change permissions on production accounts; first understand the existing ownership and configuration.

13. Debugging SSH

Verbose client output:

ssh -v USER@SERVER
More detail: 
ssh -vv USER@SERVER
Even more: 
ssh -vvv USER@SERVER

Verbose output helps identify whether failure occurs during network connection, host verification or authentication.

14. Check SSH Port

On the server:

ss -ltnp | grep ':22'

Service status:

systemctl status ssh

systemctl status sshd

15. SSH Logs

Depending on distribution:

journalctl -u ssh

journalctl -u sshd

Authentication-related events may also appear in distribution-specific security or authentication logs.

16. SCP

Copy a local file to a remote host:

scp FILE USER@SERVER:/remote/path/

Copy a remote file locally:

scp USER@SERVER:/remote/file .

Custom SSH port:

scp -P PORT FILE USER@SERVER:/remote/path/

17. SFTP

sftp USER@SERVER

SFTP provides file transfer over SSH.

18. SSH Agent

An SSH agent can hold usable key identities for the current session.

Inspect: 
ssh-add -l

Agent usage is especially common when managing multiple SSH connections.

19. SSH Tunneling Concept

SSH can securely forward network connections through an SSH session.

Conceptual local-forward format: 
ssh -L LOCAL_PORT:DESTINATION:DEST_PORT USER@SERVER

This is useful for securely reaching services through a controlled host. We will cover tunneling more deeply later in networking labs.

20. Bastion / Jump Host Concept

Production environments may expose only a controlled bastion or jump host instead of every internal server directly.

OpenSSH supports jump hosts using: 
ssh -J JUMP_HOST USER@TARGET

This is common in cloud and private-network environments.

21. SSH Security Principles

  • Use least privilege
  • Protect private keys
  • Avoid sharing credentials
  • Use dedicated accounts where appropriate
  • Limit unnecessary remote access
  • Keep SSH software updated
  • Review authentication logs
  • Use key authentication appropriately
  • Avoid normal application workloads running as root

🔥 Production Scenario 1 — Connection Refused

You run:

ssh USER@SERVER
and receive connection refused. Check: 
ping -c 2 SERVER

ip route get SERVER_IP

systemctl status ssh

systemctl status sshd

ss -ltnp | grep ':22'

Possible causes:

  • SSH service stopped
  • Wrong port
  • Service not listening
  • Host firewall
  • Incorrect destination

🔥 Production Scenario 2 — Connection Timeout

Check:

ping -c 2 SERVER_IP

ip route get SERVER_IP

tracepath SERVER_IP

Possible causes:

  • Routing failure
  • Firewall dropping traffic
  • Remote host unavailable
  • Network path failure
  • Cloud security control

🔥 Production Scenario 3 — Permission Denied (publickey)

Debug from client:

ssh -vvv USER@SERVER

On server, check:

id USER

ls -ld /home/USER

ls -ld /home/USER/.ssh

ls -l /home/USER/.ssh/authorized_keys

Investigate:

  • Wrong username
  • Wrong key
  • Public key missing
  • Bad ownership
  • Bad permissions
  • Server authentication configuration

🔥 Production Scenario 4 — Host Key Changed

SSH warns that the remote host identification changed.

Do not automatically bypass the warning. First determine whether:

  • The server was legitimately rebuilt
  • The IP now belongs to another system
  • DNS changed
  • The server's host keys legitimately changed
  • There is an unexpected security issue

Verify the new server identity through a trusted method before updating your local known_hosts entry.

🔥 Production Scenario 5 — Works for Root, Fails for App User

id APP_USER

ls -ld /home/APP_USER

ls -ld /home/APP_USER/.ssh

ls -l /home/APP_USER/.ssh/authorized_keys

Check user existence, shell, home directory, permissions and authentication configuration.

🔥 Production Scenario 6 — SSH Suddenly Slow

Check:

ssh -vv USER@SERVER

getent hosts SERVER

ping -c 4 SERVER

Potential causes include DNS delays, network latency, server resource pressure or authentication dependencies.

🧪 Safe Hands-On Lab

Inspect your local SSH configuration:

ssh -V

ls -la ~/.ssh 2>/dev/null

cat ~/.ssh/config 2>/dev/null || true

ssh-add -l 2>/dev/null || true

🧪 SSH Key Lab

If you do not already have a test key and want a separate lab key, you can create one without overwriting your normal key: 

ssh-keygen -t ed25519 -f ~/devops-study-lab-key

Inspect only:

ls -l ~/devops-study-lab-key*

cat ~/devops-study-lab-key.pub

The file without .pub is the private key. Keep it private.

🧩 Quick Recall

SSH says Connection Refused. What do you check first?

systemctl status ssh
systemctl status sshd
ss -ltnp | grep ':22'
ip route get SERVER_IP

SSH says Permission denied (publickey). What should you investigate?

Username, selected key, authorized_keys, home/.ssh ownership and permissions, plus server authentication configuration.

What is known_hosts used for?

It stores identities of previously contacted SSH hosts and helps detect unexpected server identity changes.

🗣️ Strong Interview Answer

“When troubleshooting SSH, I separate the problem into network, SSH service and authentication layers. I first verify that I am reaching the correct server and port, then check whether sshd is running and listening. If the TCP connection succeeds, I use verbose SSH output to determine whether the failure is host verification, username, key selection or server-side authentication. For key issues, I also verify authorized_keys, ownership and permissions.”
