IP addressing, interfaces, routing, TCP/UDP, ports, sockets, DNS and real production network troubleshooting.

1. Network Interfaces

Inspect interfaces:

ip addr

ip link

ip -br addr

Look for:

  • Interface name
  • UP or DOWN state
  • IPv4 address
  • IPv6 address
  • Loopback interface

2. Loopback

The loopback interface allows a machine to communicate with itself. 

ip addr show lo

Typical IPv4 loopback:

127.0.0.1

Hostname commonly associated with it:

localhost

3. IP Address Basics

An IP address identifies a network interface on an IP network.

Example: 
192.168.1.20/24

The /24 represents the network prefix length.

4. Subnet Basics

Example:

192.168.1.20/24

A /24 network commonly corresponds to:

255.255.255.0

For DevOps work, you should understand network ranges, CIDR notation and whether two IP addresses belong to the same subnet.

5. IPv4 and IPv6

Inspect both:

ip addr

Examples:

IPv4:
192.168.1.20

IPv6:
2001:db8::20

You do not need to master every IPv6 detail immediately, but you should recognize and troubleshoot IPv4 vs IPv6 behavior.

6. Routing Table

The routing table tells Linux where network traffic should go. 

ip route
Example: 
default via 192.168.1.1 dev eth0

This means traffic without a more specific route is sent through the gateway at 192.168.1.1 using eth0.

7. Default Gateway

The default gateway is normally used to reach networks outside the local subnet.

Check: 
ip route | grep default

8. TCP vs UDP

TCP

  • Connection-oriented
  • Reliable delivery
  • Ordered data
  • Retransmission support

UDP

  • Connectionless
  • Lower overhead
  • No built-in guarantee of delivery
  • Useful for workloads where speed or simplicity matters

9. Ports

Ports help identify application endpoints on a host.

Examples: 
22    SSH
53    DNS
80    HTTP
443   HTTPS

Applications can also use custom ports such as: 

8080
3000
5000
9090

10. Listening Ports

Inspect listening sockets:

ss -tulpn
TCP listeners: 
ss -ltn
UDP listeners: 
ss -lun
Specific port: 
ss -ltnp | grep ':8080'

11. Sockets

A network socket represents a communication endpoint.

Inspect active TCP connections: 
ss -tan
Show processes where permitted: 
ss -tulpn

12. Bind Address

An application may listen only on localhost: 

127.0.0.1:8080
or on all IPv4 interfaces: 
0.0.0.0:8080

This difference is extremely important when an application works locally but cannot be reached remotely.

Check: 
ss -ltnp

13. DNS

DNS converts hostnames into IP addresses and provides other naming data.

Inspect resolution: 
getent hosts example.com
If available: 
resolvectl status
Also inspect: 
cat /etc/resolv.conf

14. /etc/hosts

Local hostname mappings can be configured here: 

cat /etc/hosts
Example: 
10.0.0.20 app-server

Local host mappings can influence name resolution before or alongside DNS, depending on system configuration.

15. /etc/resolv.conf

Inspect resolver configuration:

cat /etc/resolv.conf

Depending on the distribution, this file may be managed by another networking or resolver service.

16. Connectivity Testing

Basic IP reachability:

ping -c 4 8.8.8.8
Hostname resolution + reachability: 
ping -c 4 example.com
Application-level HTTP test: 
curl -I https://example.com

17. curl

curl is one of the most useful DevOps networking tools. 

curl http://localhost:8080

curl -I https://example.com

curl -v https://example.com

Verbose mode helps inspect connection establishment, TLS and HTTP behavior.

18. traceroute / tracepath

If installed:

traceroute example.com
or: 
tracepath example.com

These can help inspect the path traffic takes through the network.

19. DNS vs Network Troubleshooting

If this works: 

ping -c 2 8.8.8.8
but this fails: 
getent hosts example.com

the problem may be DNS-related rather than general network connectivity.

20. Local Application Test

Before blaming the network, test the service locally. 

ss -ltnp

curl http://127.0.0.1:PORT

curl http://localhost:PORT

If local access fails, the problem may be inside the application, service or local host rather than external networking.

21. Firewall Awareness

Linux systems may use firewall tools such as nftables, iptables or distribution-specific frontends.

Read-only inspection examples: 
sudo nft list ruleset
If UFW is present: 
sudo ufw status

For this learning app, we will practice firewall changes later inside controlled labs rather than modifying your laptop rules blindly.

🔥 Production Scenario 1 — Application Running but Unreachable

Start with:

systemctl status APP_SERVICE

ss -ltnp

curl http://127.0.0.1:PORT

ip addr

ip route

Check:

  • Is the service running?
  • Is the port listening?
  • Is it bound only to 127.0.0.1?
  • Does local curl work?
  • Is routing correct?
  • Is a firewall or upstream device blocking traffic?

🔥 Production Scenario 2 — DNS Failure

getent hosts APPLICATION_DOMAIN

cat /etc/resolv.conf

resolvectl status

ping -c 2 8.8.8.8

If IP connectivity works but hostname resolution fails, focus on DNS configuration and resolver availability.

🔥 Production Scenario 3 — Connection Refused

Connection refused normally means the destination host was reachable, but nothing accepted the connection on the requested endpoint, or the connection was actively rejected.

Check: 
ss -ltnp

systemctl status SERVICE_NAME

curl -v http://localhost:PORT

journalctl -u SERVICE_NAME

🔥 Production Scenario 4 — Connection Timeout

Timeouts can point toward routing, firewall, unresponsive dependencies or network path problems.

Check: 
ip addr

ip route

ping -c 2 TARGET_IP

tracepath TARGET_IP

ss -tan

Then inspect host and network firewall controls where appropriate.

🔥 Production Scenario 5 — Works Locally, Not Remotely

Classic investigation:

ss -ltnp

curl http://127.0.0.1:PORT

ip addr

If the service listens on: 

127.0.0.1:PORT

it is normally only reachable through the local loopback interface.

🔥 Production Scenario 6 — Wrong Route

Inspect:

ip route

ip route get TARGET_IP

The second command shows which route Linux intends to use for a particular destination.

🔥 Production Scenario 7 — Intermittent Network Issue

Capture basic observations:

date

ip addr

ip route

ss -tan

ping -c 10 TARGET

journalctl -k -n 100

Correlate the issue with application logs, DNS behavior, network interface events and dependency health.

🧪 Safe Hands-On Lab

Run these read-only commands:

ip -br addr

ip route

ip route get 8.8.8.8

ss -ltn

ss -tan

cat /etc/hosts

cat /etc/resolv.conf

getent hosts example.com

curl -I https://example.com

🧪 Local Port Lab

Use Python's simple HTTP server only on your local machine: 

mkdir -p ~/network-lab

cd ~/network-lab

python3 -m http.server 9000 --bind 127.0.0.1

Open another terminal and inspect: 

ss -ltn | grep 9000

curl http://127.0.0.1:9000

Press Ctrl + C in the server terminal when finished.

🧩 Quick Recall

Application is running but users cannot connect. First checks?

systemctl status APP_SERVICE
ss -ltnp
curl http://127.0.0.1:PORT
ip addr
ip route

IP works, domain does not. What area do you investigate?

DNS resolution.

getent hosts DOMAIN
cat /etc/resolv.conf
resolvectl status

What is the difference between 127.0.0.1 and 0.0.0.0 when listening?

127.0.0.1 normally limits the listener to the local loopback interface. 0.0.0.0 normally means the service listens on all IPv4 interfaces available to that socket.

🗣️ Strong Interview Answer

“When troubleshooting Linux networking, I work layer by layer. I first verify the application process and listening port, then test the service locally. After that I inspect the interface addresses, routing table and destination route. If a hostname is involved, I verify DNS separately. Finally I investigate firewall or upstream network controls. This helps me determine whether the problem is application, host networking, DNS, routing or external network infrastructure.”
