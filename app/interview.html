🎯 Linux Interview Preparation

Concept, command, architecture, troubleshooting, production incident and mock-interview practice.

⚡ Strong Answer Framework

For troubleshooting questions, answer in this order:

  1. Clarify: symptom, scope, time and impact.
  2. Check: recent changes and current system state.
  3. Measure: use commands and explain what each proves.
  4. Isolate: identify the failing layer.
  5. Fix: apply the smallest safe change.
  6. Verify: test from the user’s perspective.
  7. Prevent: monitoring, documentation and automation.
A strong interview answer explains both the command and the evidence you expect from its output.

1. Linux Concept Questions

1. What is the Linux kernel?

The kernel is the privileged core of Linux. It manages CPU scheduling, memory, devices, filesystems, networking, security and the system-call interface used by applications.

2. Kernel vs shell?

The kernel manages protected system resources. A shell is a user-space command interpreter such as Bash that starts programs, performs expansion and connects commands using pipes and redirection.

3. Process vs thread?

A process has its own virtual address space and resources. Threads are execution units inside a process and normally share its memory, open files and other resources.

4. What are PID and PPID?

PID identifies a process. PPID identifies its parent process. They can be inspected using: 

ps -o pid,ppid,stat,comm -p PID
cat /proc/PID/status
5. Zombie vs orphan process?

A zombie has exited but its parent has not collected its exit status. An orphan is still running after its parent exits and is adopted by a subreaper or PID 1.

6. What is load average?

Load average represents the average number of runnable tasks and tasks in uninterruptible sleep over 1, 5 and 15 minutes. It must be interpreted with CPU count and I/O activity.

7. What is an inode?

An inode stores filesystem metadata such as ownership, permissions, timestamps and data-block references. The filename is stored in a directory entry that points to the inode.

8. Hard link vs symbolic link?

A hard link is another directory entry for the same inode. A symbolic link is a separate file containing a path to another file. Symbolic links can cross filesystems; normal hard links cannot.

9. What do Linux permission numbers mean?

Read is 4, write is 2 and execute is 1. Values are added for owner, group and others. For example, 750 means owner rwx, group r-x and others no access.

10. What is systemd?

systemd is a system and service manager. It manages units, dependencies, startup ordering, service supervision, resource limits, timers, mounts, sockets and related system state.

11. /proc vs /sys?

/proc mainly exposes process and kernel runtime information. /sys exposes kernel objects, devices, drivers and their relationships.

12. Namespace vs cgroup?

A namespace isolates what a process can see. A cgroup accounts for and controls how many CPU, memory, I/O or process resources a group of processes can use.

13. Container vs virtual machine?

A container runs isolated processes that share the host kernel. A virtual machine normally boots a separate guest kernel using virtualized hardware.

14. What is swap?

Swap is disk-backed space used for selected memory pages. It can provide additional memory flexibility but is much slower than RAM and does not fix application memory leaks.

15. What is a file descriptor?

A file descriptor is a per-process integer representing an open kernel resource such as a file, directory, socket or pipe.

2. Command Questions

1. Find the largest files under /var 
sudo find /var \
  -xdev \
  -type f \
  -printf '%s %p\n' \
  2>/dev/null \
  | sort -n \
  | tail -20
2. Find which process listens on a port 
sudo ss -ltnp 'sport = :PORT'
sudo lsof -i :PORT
sudo fuser -v PORT/tcp
3. Show top CPU-consuming processes 
ps -eo pid,ppid,user,stat,pcpu,pmem,comm \
  --sort=-pcpu | head -20
4. Show top memory-consuming processes 
ps -eo pid,user,rss,vsz,pmem,comm \
  --sort=-rss | head -20
5. Check filesystem space and inode usage 
df -hT
df -i
6. Find deleted files still held open 
sudo lsof +L1
7. Check service logs from the last 30 minutes 
journalctl -u SERVICE_NAME \
  --since "30 minutes ago"
8. Check logs from the previous boot 
journalctl --list-boots
journalctl -b -1
journalctl -k -b -1
9. Check routing for a destination 
ip route get DESTINATION_IP
10. Test DNS using the system resolver 
getent ahosts example.com
resolvectl query example.com
11. Inspect every directory permission in a path 
namei -l /path/to/file
getfacl /path/to/file
12. Find files modified in the last day 
find /path \
  -type f \
  -mtime -1 \
  -print
13. Check open file descriptors of a process 
ls -l /proc/PID/fd
sudo lsof -p PID
cat /proc/PID/limits
14. Check a user’s identity and groups 
id USERNAME
groups USERNAME
getent passwd USERNAME
getent group GROUPNAME
15. Search recursively and case-insensitively 
grep -Rni \
  --exclude-dir=.git \
  'SEARCH_TEXT' \
  /path

3. Troubleshooting Questions

1. How would you troubleshoot high CPU? 
uptime
top
mpstat -P ALL 1 5
pidstat -u 1 5

ps -eo pid,ppid,stat,pcpu,comm \
  --sort=-pcpu | head

Identify the process and thread, determine user vs system CPU, inspect logs and recent changes, profile safely, then validate whether the workload is expected.

2. How would you troubleshoot high load but low CPU? 
vmstat 1 5
iostat -xz 1 5

ps -eo state,pid,ppid,wchan:32,comm \
  | awk '$1 ~ /D|R/'

Look for processes in uninterruptible sleep and storage or network-filesystem latency.

3. How would you troubleshoot memory exhaustion? 
free -h
vmstat 1 5

ps -eo pid,user,rss,vsz,pmem,comm \
  --sort=-rss | head

sudo journalctl -k \
  | grep -Ei 'oom|out of memory|killed process'
4. Disk is full—what do you check? 
df -hT
df -i

sudo du -xhd1 /var \
  2>/dev/null | sort -h

sudo lsof +L1

Separate block exhaustion, inode exhaustion, large data and deleted-open files before deleting anything.

5. A systemd service will not start 
systemctl status SERVICE_NAME \
  --no-pager -l

journalctl -u SERVICE_NAME \
  --since "30 minutes ago"

systemctl cat SERVICE_NAME
systemctl show SERVICE_NAME \
  -p Result -p ExecMainStatus
6. DNS resolution is failing 
cat /etc/resolv.conf
grep '^hosts:' /etc/nsswitch.conf
resolvectl status

getent ahosts example.com
dig @DNS_SERVER example.com

Test direct IP connectivity to separate DNS failure from general network failure.

7. SSH is unavailable 
ssh -vvv USER@SERVER

sudo sshd -t
sudo ss -ltnp | grep ':22'
sudo systemctl status ssh sshd
sudo journalctl -u ssh -u sshd

Check routing, firewall, daemon, user, keys, permissions and SELinux/AppArmor. Keep any working SSH session open.

8. Application gets permission denied 
id
namei -l /path/to/file
getfacl /path/to/file
findmnt -T /path/to/file

ls -lZ /path/to/file
sudo ausearch -m AVC -ts recent
9. Filesystem will not mount 
lsblk -f
sudo blkid
findmnt --verify
cat /etc/fstab

sudo journalctl -b \
  | grep -Ei 'mount|filesystem|fsck'
10. Server fails after reboot 
systemctl --failed
journalctl -xb
journalctl -p err -b

lsblk -f
findmnt --verify
systemd-analyze critical-chain

4. Scenario-Based Questions

1. Application works manually but fails in systemd

Compare:

  • User and group
  • Environment and PATH
  • Working directory
  • Resource limits
  • Filesystem access
  • systemd sandboxing
systemctl cat SERVICE_NAME

systemctl show SERVICE_NAME \
  -p User \
  -p Group \
  -p Environment \
  -p WorkingDirectory \
  -p ExecStart \
  -p LimitNOFILE
2. Service works locally but not remotely 
sudo ss -ltnp
curl http://127.0.0.1:PORT
curl http://SERVER_IP:PORT

sudo nft list ruleset
ip route

Check whether it listens only on loopback, then verify host firewall, external firewall, routing and load balancer.

3. df shows full but du does not 
df -hT
sudo du -xsh /
sudo lsof +L1
findmnt

Look for deleted-open files, hidden data beneath mounts or different filesystem boundaries.

4. kill -9 does not remove a process 
ps -o pid,ppid,stat,wchan:30,comm -p PID
cat /proc/PID/status

It may be in uninterruptible kernel sleep or already be a zombie waiting for its parent to collect its exit status.

5. Application becomes unavailable after every reboot 
systemctl is-enabled SERVICE_NAME
systemctl status SERVICE_NAME
systemctl list-dependencies SERVICE_NAME
journalctl -b -u SERVICE_NAME
systemd-analyze critical-chain

Check enablement, dependency ordering, storage mounts, network-online requirements, secrets and startup configuration.

6. Container exits immediately 
docker ps -a
docker logs CONTAINER_NAME

docker inspect \
  --format '{{json .State}}' \
  CONTAINER_NAME

docker inspect \
  --format '{{json .Config.Entrypoint}} {{json .Config.Cmd}}' \
  CONTAINER_NAME
7. Container is OOM-killed 
docker inspect \
  --format '{{.State.OOMKilled}}' \
  CONTAINER_NAME

docker stats --no-stream

sudo journalctl -k \
  | grep -Ei 'oom|out of memory|killed process'
8. Application is intermittently slow

Correlate latency with CPU, memory, storage, network, database, dependency and deployment metrics. Compare normal and slow request traces using a precise time window. 

vmstat 1 5
iostat -xz 1 5
pidstat -u -r -d 1 5
ss -s
journalctl -u SERVICE_NAME \
  --since "30 minutes ago"

5. Production Incident Questions

Incident 1 — Root filesystem reaches 100%
  1. Confirm impact using df -hT and df -i.
  2. Identify the filesystem and largest directories.
  3. Check deleted-open files.
  4. Protect critical services and preserve evidence.
  5. Apply a safe recovery action.
  6. Verify writes and application health.
  7. Fix retention, rotation or growth monitoring.
Incident 2 — Server load rises after deployment
  1. Record deployment time and affected hosts.
  2. Compare CPU, memory, I/O and request rate before and after.
  3. Identify hot processes and threads.
  4. Check errors, retries and dependency latency.
  5. Roll back if the deployment is the confirmed cause.
  6. Validate recovery and create regression tests.
Incident 3 — SSH unavailable on every production server
  1. Use approved console or out-of-band access.
  2. Check whether a shared firewall or configuration change occurred.
  3. Validate SSH configuration before reloading.
  4. Restore access using a controlled canary host.
  5. Verify named-account and key authentication.
  6. Review change controls and staged rollout safeguards.
Incident 4 — Service is healthy but users receive errors

“Running” only confirms the process state. Check the complete request path: DNS, load balancer, proxy, port, application health, database, external dependencies and user-specific authorization.

Incident 5 — Memory leak causes daily restarts
  1. Graph memory growth over time.
  2. Separate RSS, cache and cgroup usage.
  3. Capture application profiles before restart.
  4. Use a temporary limit or controlled restart only as mitigation.
  5. Fix the leak and validate under realistic load.

6. Architecture Explanation Questions

1. Explain the Linux boot process
  1. Firmware performs hardware initialization.
  2. Bootloader selects and loads the kernel and initramfs.
  3. Kernel initializes CPU, memory and drivers.
  4. Initramfs prepares the real root filesystem.
  5. Kernel starts PID 1, commonly systemd.
  6. systemd starts targets, services, mounts and sockets.
2. Explain what happens when a command runs
  1. Shell parses and expands the command.
  2. Shell resolves the executable using PATH or a direct path.
  3. A child process is created.
  4. The executable is loaded with execve.
  5. Dynamic libraries are mapped when required.
  6. The process uses system calls for kernel operations.
  7. The parent collects the exit status.
3. Explain a network request to a Linux service
  1. DNS resolves the hostname.
  2. The client selects a route and creates a socket.
  3. Packets travel through network interfaces and firewalls.
  4. The server kernel matches the destination port to a socket.
  5. The application accepts and processes the request.
  6. The response follows the routing path back.
4. Explain systemd service management

systemd reads unit configuration and dependencies, creates the service process with the configured user, environment, limits and sandbox, monitors its state and records service logs in the journal.

5. Explain Linux container architecture

Containers are host-kernel processes. Namespaces isolate their views, cgroups control resources, capabilities reduce privilege, seccomp filters system calls, mandatory access controls enforce policy and layered filesystems provide image and writable layers.

6. Explain Linux storage from disk to file

A physical or virtual block device may contain partitions, RAID, encryption or LVM. A filesystem organizes files and metadata on the resulting block device, and a mount attaches that filesystem to the directory tree.

7. Debugging Methodology

Layer-by-layer model

  1. Client and user input
  2. DNS
  3. Network route and firewall
  4. Port and socket
  5. Service manager
  6. Application
  7. Database and dependencies
  8. CPU, memory and storage
  9. Kernel and hardware

Evidence categories

Evidence Examples
State systemctl, ps, ss, ip, findmnt
Logs journalctl, application and audit logs
Metrics CPU, memory, latency, errors and saturation
Changes Deployment, package, configuration and infrastructure changes
Comparison Working host, previous version or normal time window
Avoid random changes. Every command should test a hypothesis, reduce the possible causes or safely validate recovery.

9. Mock Interview — Mid Level

  1. Explain the Linux boot process.
  2. Why can load average be high while CPU is low?
  3. How would you troubleshoot a failed systemd service?
  4. How do permissions, ACLs and SELinux interact?
  5. Why can df and du disagree?
  6. How would you investigate an OOM kill?
  7. Explain PID, mount and network namespaces.
  8. Explain LVM and online volume expansion.
  9. How do you troubleshoot intermittent DNS failures?
  10. How would you make a Bash automation script production-safe?

Expected level

Use a structured diagnostic flow, explain expected evidence, avoid unsafe fixes and include verification.

10. Mock Interview — Senior / Production Level

  1. A fleet-wide SSH configuration change locks out administrators. Explain containment, recovery and prevention.
  2. An application is healthy according to systemd but users receive timeouts. Walk through the complete request path.
  3. A deployment doubles CPU usage without increasing traffic. Explain investigation and rollback criteria.
  4. A container is repeatedly OOM-killed despite apparently low host memory usage. Explain system and cgroup analysis.
  5. Storage latency rises only during backups. Explain measurement, resource contention and remediation.
  6. Design monitoring for CPU, memory, disk, network, services, logs and user-visible availability.
  7. Explain how you would write and test a production incident runbook.
  8. Explain a post-incident review without blaming individuals.

Expected level

Include impact, incident coordination, evidence preservation, safe mitigation, root-cause analysis, validation, monitoring, automation and long-term prevention.
