👤 Users, Groups & Permissions

Linux identity, ownership, permissions, sudo, ACLs, special permissions and production access troubleshooting.

For almost every Permission Denied problem, ask:

  • Which user is the process running as?
  • Who owns the file?
  • Which group owns it?
  • What permissions exist?
  • Can the user traverse parent directories?
  • Is an ACL or security policy involved?

1. Users

Every Linux process executes under a user identity. 

whoami

id

id USERNAME

getent passwd USERNAME

Important:

  • UID 0 = root
  • Normal users generally have non-zero UIDs
  • Services often use dedicated service accounts

2. /etc/passwd

cat /etc/passwd
Example format: 
username:x:UID:GID:comment:home:shell

Fields include:

  • Username
  • UID
  • Primary GID
  • Home directory
  • Login shell

3. /etc/shadow

sudo cat /etc/shadow

Password hashes and password-aging information are stored here. The file is protected because this information is security-sensitive.

4. Groups

groups

groups USER

getent group

getent group GROUP_NAME

A user can have:

  • One primary group
  • Multiple supplementary groups

5. User Management

useradd USER

useradd -m USER

passwd USER

usermod -aG GROUP USER

userdel USER

Be careful with: 

usermod -G GROUP USER

Without -a, supplementary group membership can be replaced.

6. Group Management

groupadd devops

groupdel devops

usermod -aG devops USER

getent group devops

7. File Ownership

ls -l FILE

chown USER FILE

chown USER:GROUP FILE

chgrp GROUP FILE
Example: 
chown appuser:appgroup /opt/app/config.yaml

8. Read, Write & Execute

r = read
w = write
x = execute
Example: 
-rwxr-x---
Interpretation: 
Owner  = rwx
Group  = r-x
Others = ---

9. Numeric Permissions

Read    = 4
Write   = 2
Execute = 1
Examples: 
7 = rwx
6 = rw-
5 = r-x
4 = r--
Therefore: 
chmod 755 script.sh
means: 
Owner  = rwx
Group  = r-x
Others = r-x

10. Directory Permissions

Directory permissions behave differently from normal files.

  • r — list names
  • w — create/delete entries
  • x — traverse/access directory contents

This is important when troubleshooting permissions on deeply nested paths.

11. Troubleshooting Parent Directories

A file may have correct permissions but still be inaccessible because a parent directory cannot be traversed.

Use: 
namei -l /opt/application/config/app.conf
This shows permissions for every directory in the path.

12. umask

umask

umask 022

umask controls which permission bits are removed when new files and directories are created.

Typical starting permissions: 
Files       666
Directories 777
Example: 
umask 022

File:
666 - 022 → typically 644

Directory:
777 - 022 → typically 755

13. sudo

sudo allows controlled privilege escalation. 

sudo COMMAND

sudo -l

sudo -l -U USER
Safely edit sudo configuration with: 
visudo

Production principle: give only the privileges actually required.

14. ACLs

ACLs allow more detailed permissions beyond traditional owner/group/others permissions.

Inspect: 
getfacl FILE
Grant access: 
setfacl -m u:USER:rwx FILE
Remove ACL: 
setfacl -x u:USER FILE

15. Sticky Bit

Common example: 
ls -ld /tmp
Often looks similar to: 
drwxrwxrwt
The sticky bit helps prevent users from deleting other users' files in a shared writable directory.

16. SetUID

SetUID can cause an executable to run using the file owner's effective identity. Inspect: 
find /usr/bin -perm -4000 2>/dev/null

This has security implications and should be understood carefully.

17. SetGID

On directories, SetGID can cause newly created files to inherit the directory's group.

Example: 
chmod g+s shared-directory
Useful for shared team directories.

18. Service Accounts

Production services should commonly run with dedicated, least-privileged accounts instead of root.

Examples: 
www-data

nginx

postgres
Check service identity: 
systemctl show SERVICE_NAME --property=User

ps aux | grep PROCESS

🔥 Production Scenario 1 — Permission Denied

An application cannot read: 

/opt/app/config/app.conf
Investigation: 
systemctl show APP_SERVICE --property=User

id APP_USER

ls -l /opt/app/config/app.conf

namei -l /opt/app/config/app.conf

getfacl /opt/app/config/app.conf
Check:
  • Runtime user
  • File owner
  • Group
  • File mode
  • Parent directory execute permission
  • ACLs

🔥 Production Scenario 2 — Works as Root Only

Deployment succeeds as root but fails as the CI/CD service account.

Compare: 
id root

id CI_USER

sudo -l -U CI_USER

ls -ld /deployment/path

namei -l /deployment/path/application

Never solve every permission problem by simply running everything as root. Find the actual required access.

🔥 Production Scenario 3 — Group Access Failure

A user was added to a group but access still fails.

Check: 
id USER

groups USER

getent group GROUP
A new login session may be required for group membership to be reflected in the user's session.

🗣️ Production Interview Answer

“When I troubleshoot a permission issue, I first identify the actual user running the process. Then I inspect the file owner, group and mode. I also inspect every parent directory because directory execute permission controls traversal. If traditional permissions look correct, I check ACLs, sudo configuration and, where applicable, additional security controls. I prefer fixing the minimum required access instead of running the application as root.”
