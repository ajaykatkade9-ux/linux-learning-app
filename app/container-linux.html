🐳 DevOps / Container Linux

Understand containers as Linux processes using namespaces, cgroups, layered filesystems, networking and security controls.

⚡ 60-Second Revision

  • A container is an isolated process running on the host kernel.
  • An image is an immutable application filesystem template.
  • A running container adds a writable layer.
  • Namespaces isolate what processes can see.
  • cgroups account for and limit resources.
  • Capabilities reduce root privilege.
  • Container networking commonly uses veth pairs and bridges.
  • Volumes store persistent data outside the writable layer.
  • PID 1 must handle signals and reap child processes.
  • Containers share the host kernel and are not virtual machines.

1. Containers vs Virtual Machines

Container Virtual machine
Shares the host kernel Runs a separate guest kernel
Starts as isolated processes Boots a complete operating system
Usually smaller and faster to start Usually needs more CPU, RAM and storage
Isolation through Linux kernel features Isolation through a hypervisor
Linux host-kernel compatibility required Can run a different guest operating system
Containers package applications and dependencies, but they still depend on the host kernel for process, memory, storage and network operations.

2. Container Architecture

Component Purpose
Docker or Podman CLI User-facing container commands
Container engine Images, lifecycle, networking and storage management
OCI runtime Creates the final Linux container process
Linux kernel Namespaces, cgroups, capabilities, seccomp and filesystems

Inspect installed tools:

docker version
docker info

podman version
podman info

runc --version

Docker commonly uses a long-running engine service. Podman is designed around a daemonless model and supports rootless containers.

3. Images and Containers

Image Container
Read-only application template Running or stopped instance of an image
Built from filesystem layers Adds runtime state and a writable layer
Identified by name, tag and digest Identified by container ID and name 
docker images

Podman equivalents:

podman images

podman history IMAGE_NAME

podman ps

Tags can move between image versions. Production deployments often use immutable image digests for exact identification.

4. Container Processes

The command configured for the container becomes its primary process. When this process exits, the container stops. 

docker ps
docker top CONTAINER_NAME
docker inspect \
  --format '{{.State.Pid}}' \
  CONTAINER_NAME

podman top CONTAINER_NAME
podman inspect \
  --format '{{.State.Pid}}' \
  CONTAINER_NAME

Inspect from the host:

PID=HOST_PID

ps -fp $PID
pstree -p $PID
cat /proc/$PID/status
cat /proc/$PID/cgroup
ls -l /proc/$PID/ns

Run a diagnostic command inside:

docker exec CONTAINER_NAME ps -ef
docker exec -it CONTAINER_NAME sh

podman exec CONTAINER_NAME ps -ef
podman exec -it CONTAINER_NAME sh
docker exec creates an additional process inside the existing container namespaces. It does not create a new container.

5. PID Namespace and PID 1

PID namespaces allow processes to have different process IDs inside and outside the container. 

HOST_PID=$(
  docker inspect \
  --format '{{.State.Pid}}' \
  CONTAINER_NAME
)

echo "$HOST_PID"

ps -fp "$HOST_PID"

docker exec CONTAINER_NAME \
  ps -eo pid,ppid,stat,comm

Compare namespace identifiers:

readlink /proc/1/ns/pid
readlink /proc/$HOST_PID/ns/pid

PID 1 responsibilities

  • Receive termination signals correctly
  • Shut down the application gracefully
  • Reap exited child processes
  • Return a meaningful exit status

Inspect signal configuration:

docker inspect \
  --format '{{.Config.StopSignal}}' \
  CONTAINER_NAME

docker stop \
  --time 20 \
  CONTAINER_NAME
Shell wrapper scripts can prevent signals from reaching the real application. Use exec application when appropriate so the application replaces the wrapper process.

6. Linux Namespaces Used by Containers

Namespace Container isolation
PID Process ID tree
Network Interfaces, routes, sockets and firewall state
Mount Filesystem mount view
UTS Hostname and domain name
IPC Shared memory and message queues
User User and group ID mapping
cgroup View of the cgroup hierarchy 
lsns
ls -l /proc/HOST_PID/ns

docker inspect \
  --format '{{.State.Pid}}' \
  CONTAINER_NAME

Enter selected container namespaces from the host:

sudo nsenter \
  --target HOST_PID \
  --mount \
  --uts \
  --ipc \
  --net \
  --pid
nsenter can bypass normal container tooling and exposes a powerful host-level debugging path. Restrict its use in production.

8. Port Publishing

Publishing a port maps a host address and port to a container port. 

docker run \
  --name web-demo \
  -d \
  -p 127.0.0.1:8080:80 \
  nginx

docker port web-demo
sudo ss -ltnp | grep ':8080'
curl http://127.0.0.1:8080
Configuration Meaning
127.0.0.1:8080:80 Host-local access only
8080:80 Normally published on all host interfaces
80 Container port only; not automatically host-published
Publishing a port can expose the service beyond the host. Verify the bind address, firewall and external security rules.

9. Network Namespace Debugging

Obtain the container host PID:

PID=$(
  docker inspect \
  --format '{{.State.Pid}}' \
  CONTAINER_NAME
)

Run host tools inside its network namespace:

sudo nsenter -t "$PID" -n ip address
sudo nsenter -t "$PID" -n ip route
sudo nsenter -t "$PID" -n ss -lntup
sudo nsenter -t "$PID" -n cat /etc/resolv.conf

Container-side checks:

docker exec CONTAINER_NAME \
  cat /etc/resolv.conf

docker exec CONTAINER_NAME \
  getent hosts DESTINATION

docker exec CONTAINER_NAME \
  ip route
Minimal images may not contain tools such as ip, ss, curl or a shell. Host namespace tools are useful when modifying the image is undesirable.

10. Container Filesystems

Container images are built from read-only layers. A running container receives a writable layer using copy-on-write behaviour. 

docker info \
  --format '{{.Driver}}'

docker image inspect IMAGE_NAME
docker history IMAGE_NAME

docker inspect \
  --format '{{json .GraphDriver}}' \
  CONTAINER_NAME

docker diff CONTAINER_NAME

OverlayFS model

Layer Purpose
lowerdir Read-only image layers
upperdir Container changes
workdir OverlayFS internal working directory
merged Combined filesystem visible to the container
Storage implementation varies by engine and version. Inspect the active engine rather than assuming every host uses overlay2.

11. Mount Namespaces

A mount namespace gives a container its own view of filesystem mounts while still using host-kernel filesystem operations. 

PID=$(
  docker inspect \
  --format '{{.State.Pid}}' \
  CONTAINER_NAME
)

readlink /proc/$PID/ns/mnt
cat /proc/$PID/mountinfo
sudo nsenter -t "$PID" -m findmnt

Compare host and container roots:

ls -ld /
sudo ls -ld /proc/$PID/root
sudo ls /proc/$PID/root
Accessing /proc/PID/root from the host can bypass the normal container interface. Use it only for controlled investigation.

12. Persistent Storage

Storage type Use
Writable layer Temporary container-specific changes
Named volume Engine-managed persistent data
Bind mount Specific host path exposed inside container
tmpfs Temporary memory-backed data 
docker volume ls
docker volume inspect VOLUME_NAME

docker inspect \
  --format '{{json .Mounts}}' \
  CONTAINER_NAME

Example named volume:

docker run \
  --name data-demo \
  --mount \
  source=app-data,target=/var/lib/app \
  IMAGE_NAME

Example read-only bind mount:

docker run \
  --mount \
  type=bind,source=/host/config,target=/app/config,readonly \
  IMAGE_NAME
Bind mounts expose host paths. Incorrect writable mounts can allow a compromised container to change important host data.

13. cgroups and Resource Limits

Containers without explicit limits may consume resources according to whatever the host kernel and runtime permit. 

docker stats
docker inspect \
  --format '{{json .HostConfig}}' \
  CONTAINER_NAME

podman stats
podman inspect CONTAINER_NAME

Example resource limits:

docker run \
  --name limited-app \
  --memory 512m \
  --memory-swap 512m \
  --cpus 1.5 \
  --pids-limit 200 \
  IMAGE_NAME

Inspect the host cgroup:

PID=$(
  docker inspect \
  --format '{{.State.Pid}}' \
  CONTAINER_NAME
)

cat /proc/$PID/cgroup
systemd-cgls
systemd-cgtop

Relevant cgroup v2 files:

memory.current
memory.max
memory.events
cpu.max
cpu.stat
pids.current
pids.max
io.stat

14. Container OOM Investigation

docker inspect \
  --format '{{.State.OOMKilled}}' \
  CONTAINER_NAME

docker stats --no-stream

sudo journalctl -k \
  | grep -Ei 'oom|out of memory|killed process'

For the container cgroup:

cat memory.current
cat memory.max
cat memory.events
cat memory.stat
  1. Confirm whether the container was OOM-killed.
  2. Compare usage against the configured memory limit.
  3. Check application memory metrics and traffic changes.
  4. Identify a leak, spike, cache or incorrect limit.
  5. Fix application behaviour or right-size the limit.

15. Linux Capabilities in Containers

Container root normally receives a reduced capability set, but still has more privilege than a regular non-root process. 

docker exec CONTAINER_NAME \
  grep '^Cap' /proc/1/status

docker exec CONTAINER_NAME \
  capsh --print

getpcaps HOST_PID

Drop all capabilities and add only one:

docker run \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  IMAGE_NAME

Additional hardening:

docker run \
  --user 10001:10001 \
  --read-only \
  --tmpfs /tmp \
  --security-opt no-new-privileges \
  --cap-drop ALL \
  IMAGE_NAME
Avoid --privileged unless there is a documented, reviewed requirement. It removes major isolation protections.

16. Container Security Layers

  • Run as a non-root user.
  • Drop unnecessary capabilities.
  • Use the default seccomp profile.
  • Keep SELinux or AppArmor enabled.
  • Use read-only filesystems where possible.
  • Restrict writable bind mounts.
  • Set memory, CPU and PID limits.
  • Do not mount the container-engine socket unnecessarily.
  • Use trusted minimal images.
  • Scan and patch images regularly.
  • Keep secrets outside image layers.

Inspect security settings:

docker inspect \
  --format '{{json .HostConfig.SecurityOpt}}' \
  CONTAINER_NAME

docker inspect \
  --format '{{.HostConfig.Privileged}}' \
  CONTAINER_NAME

docker inspect \
  --format '{{json .HostConfig.CapDrop}}' \
  CONTAINER_NAME

  5. Check OOM status and resource limits.

19. Production Scenario — Port Not Reachable

docker ps

docker inspect \
  --format '{{json .NetworkSettings.Ports}}' \
  CONTAINER_NAME

sudo ss -lntup
curl -v http://127.0.0.1:HOST_PORT

docker exec CONTAINER_NAME \
  ss -lntup

Verify:

  • The application is running.
  • It listens on the expected container port.
  • It listens on more than container loopback when required.
  • The port is published to the correct host address.
  • Host and cloud firewalls permit access.

20. Production Scenario — Container DNS Failure

docker exec CONTAINER_NAME \
  cat /etc/resolv.conf

docker exec CONTAINER_NAME \
  getent hosts DESTINATION

docker network inspect NETWORK_NAME

resolvectl status
getent hosts DESTINATION
  1. Compare host and container DNS.
  2. Check container network attachment.
  3. Check the embedded container DNS service.
  4. Check upstream resolvers and firewall rules.
  5. Verify the requested service name and network scope.

21. Production Scenario — Volume Permission Denied

docker inspect \
  --format '{{json .Mounts}}' \
  CONTAINER_NAME

docker inspect \
  --format '{{.Config.User}}' \
  CONTAINER_NAME

docker exec CONTAINER_NAME id

namei -l /HOST/PATH
getfacl /HOST/PATH
ls -ldZ /HOST/PATH

Check:

  • Container UID and GID
  • Host ownership and permissions
  • ACL rules
  • SELinux labels
  • Read-only mount options
  • Rootless user ID mapping
Do not use recursive chmod 777. Map the application UID/GID and grant only the required access.

22. Production Scenario — Container Disk Growth

docker system df
docker system df -v

docker ps \
  --size

docker inspect \
  --format '{{.LogPath}}' \
  CONTAINER_NAME

sudo du -sh \
  /var/lib/docker/* \
  2>/dev/null

Common causes:

  • Unbounded container logs
  • Application data written into the writable layer
  • Unused images and build cache
  • Stopped containers
  • Orphaned volumes
Cleanup commands can remove recoverable or required data. Inspect exact targets and backup requirements before deleting images, containers, cache or volumes.

🎯 Interview Questions

Is a container a lightweight virtual machine?

No. A Linux container is an isolated group of processes sharing the host kernel. A VM normally runs a separate guest kernel.

Namespace vs cgroup?

Namespaces isolate what a process can see. cgroups account for and limit how many resources processes can use.

Why is PID 1 special?

It must handle termination signals correctly and reap exited child processes to prevent zombies.

Image vs container?

An image is an immutable layered template. A container is a running or stopped instance with runtime state and a writable layer.

Volume vs bind mount?

A volume is managed by the container engine. A bind mount exposes a specific host filesystem path inside the container.

How does container port publishing work?

The runtime configures host networking so traffic received on a host address and port reaches a port in the container network namespace.

Why avoid privileged containers?

Privileged mode grants broad device and kernel access and removes many isolation controls, greatly increasing host-compromise risk.

How do you debug a container without tools?

Obtain its host PID and use host tools with nsenter, or use a controlled diagnostic container sharing the target namespaces.

✅ Production Checklist

  • Run containers as non-root.
  • Set CPU, memory and PID limits.
  • Drop unnecessary capabilities.
  • Avoid privileged mode.
  • Keep seccomp and SELinux/AppArmor enabled.
  • Use read-only filesystems where practical.
  • Store persistent data in appropriate volumes.
  • Restrict writable bind mounts.
  • Configure container log rotation.
  • Use health checks and graceful shutdown.
  • Scan and update container images.
  • Keep secrets outside images and logs.
  • Monitor container and host resources together.
