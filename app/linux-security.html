🛡️ Linux Security

Learn how to reduce attack surface, protect access, harden services, investigate security events and secure production Linux systems.

⚡ 60-Second Revision

  • Apply least privilege.
  • Disable unnecessary services and ports.
  • Patch operating systems and applications.
  • Use SSH keys and restrict privileged access.
  • Configure a host firewall.
  • Keep SELinux or AppArmor enforced.
  • Protect secrets and encrypt sensitive data.
  • Collect logs and audit important changes.
  • Harden systemd services and kernel settings.
  • Test backups and incident-response procedures.

1. Linux Security Layers

Layer Purpose Examples
Physical Prevent unauthorized hardware access Datacenter access, encrypted disks, Secure Boot
Identity Verify users and services Passwords, SSH keys, MFA, service accounts
Authorization Control allowed actions Permissions, sudo, ACL, capabilities
Network Restrict communication nftables, firewalld, UFW, security groups
Application Confine applications SELinux, AppArmor, systemd sandboxing
Detection Identify suspicious activity journald, auditd, IDS, file-integrity monitoring
Recovery Restore trusted operation Backups, rebuilds, incident-response plans
Security is defence in depth. A firewall alone cannot protect weak passwords, vulnerable software or excessive privileges.

2. Security Baseline

Identify the system before changing it:

cat /etc/os-release
uname -r
hostnamectl
uptime
who
w

Find listening services:

sudo ss -tulpn
sudo systemctl --type=service --state=running
sudo systemctl list-unit-files --state=enabled

Check recently authenticated users:

last
lastlog
sudo lastb
sudo journalctl -u ssh --since today
sudo journalctl -u sshd --since today

Service names differ between distributions. Ubuntu commonly uses ssh; RHEL-family systems commonly use sshd.

3. Reduce Attack Surface

Every unnecessary package, service and open port increases the number of components that must be protected. 

# Inspect a service
systemctl status SERVICE_NAME
systemctl cat SERVICE_NAME

# Stop and disable only after confirming it is unnecessary
sudo systemctl disable --now SERVICE_NAME

# Prevent accidental activation when appropriate
sudo systemctl mask SERVICE_NAME
Never disable SSH, networking, firewall or authentication services on a remote production server without console access and a tested recovery plan.

4. Updates and Vulnerability Reduction

Debian and Ubuntu

sudo apt update
apt list --upgradable
sudo apt upgrade

RHEL, Rocky, AlmaLinux and Fedora

sudo dnf check-update
sudo dnf upgrade

Check whether a reboot may be required:

# Ubuntu/Debian
test -f /var/run/reboot-required && cat /var/run/reboot-required

# RHEL-family when needs-restarting is available
sudo needs-restarting -r
Production patching requires tested backups, maintenance windows, application health checks and rollback planning.

5. SSH Hardening

Main server configuration:

/etc/ssh/sshd_config

Inspect effective configuration:

sudo sshd -T

Common hardening directives:

PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
PermitEmptyPasswords no
MaxAuthTries 3
X11Forwarding no
AllowUsers deploy
Do not disable password login until key-based login has been tested in a second terminal. Keep the original SSH session open while testing.

Validate before reload:

sudo sshd -t

# Ubuntu/Debian
sudo systemctl reload ssh

# RHEL-family
sudo systemctl reload sshd

Inspect authorized keys and permissions:

ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys

chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

Recommended private-key permissions:

chmod 600 ~/.ssh/id_ed25519

6. Host Firewall

Always allow the management connection before enabling or replacing firewall rules on a remote server.

UFW

sudo ufw status verbose
sudo ufw allow OpenSSH
sudo ufw enable
sudo ufw status numbered

firewalld

sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-all
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --reload

nftables

sudo nft list ruleset
sudo nft list tables
sudo nft list ruleset -a
Never run a command that flushes the production firewall remotely unless console access and a recovery procedure are available.

7. SELinux

SELinux applies Mandatory Access Control in addition to normal Linux permissions. 

getenforce
sestatus
ls -Z
ps -eZ

Modes:

  • Enforcing: policy is enforced and denials are logged.
  • Permissive: denials are logged but not enforced.
  • Disabled: SELinux policy is not active.

Investigate recent denials:

sudo ausearch -m AVC -ts recent
sudo journalctl -t setroubleshoot --since today

Restore expected labels:

sudo restorecon -Rv /path/to/directory

Create a persistent custom file-context rule:

sudo semanage fcontext -a \
  -t httpd_sys_content_t \
  "/srv/site(/.*)?"

sudo restorecon -Rv /srv/site

Inspect and enable a required boolean:

getsebool -a
getsebool httpd_can_network_connect

sudo setsebool -P \
  httpd_can_network_connect on
Disabling SELinux is not a production fix. Read the denial, correct labels or policy, test the application, and keep enforcing mode enabled.

8. AppArmor

AppArmor confines programs using profiles, commonly identified by executable paths. 

sudo aa-status
sudo apparmor_status
ls /etc/apparmor.d/

Inspect denials:

sudo journalctl -k | grep -i apparmor
sudo journalctl -k | grep -i denied

Profile modes:

sudo aa-complain /path/to/program
sudo aa-enforce /path/to/program

Reload a modified profile:

sudo apparmor_parser -r \
  /etc/apparmor.d/PROFILE_NAME
Use complain mode temporarily while developing or debugging a profile. Return the validated profile to enforce mode.

9. Linux Capabilities

Capabilities divide traditional root privileges into smaller units. This allows a process to receive only the privilege it requires. 

getcap /path/to/binary
sudo getcap -r / 2>/dev/null
capsh --print

Example: allow a binary to bind a privileged port:

sudo setcap \
  cap_net_bind_service=+ep \
  /path/to/binary

Remove file capabilities:

sudo setcap -r /path/to/binary
Capabilities are privileges. Grant only the required capability, document it, and review it after package upgrades.

10. PAM and Authentication

Pluggable Authentication Modules control authentication, account restrictions, password policy and session handling. 

ls /etc/pam.d/
cat /etc/pam.d/sshd
cat /etc/login.defs

passwd -S USERNAME
chage -l USERNAME

Common controls include:

  • Password-quality requirements
  • Failed-login lockouts
  • Password expiry
  • Session limits
  • Multi-factor authentication integrations
PAM configuration is distribution-specific. A syntax mistake can block every login. Keep root console access and create a backup before editing PAM files.

11. sudo Security

Always edit sudo policy through:

sudo visudo

Validate a separate sudoers file:

sudo visudo -cf /etc/sudoers.d/FILE_NAME

Inspect privileges:

sudo -l
sudo -l -U USERNAME

Prefer specific commands:

deploy ALL=(root) /usr/bin/systemctl restart myapp

Avoid unrestricted rules such as:

deploy ALL=(ALL) NOPASSWD: ALL

12. auditd

The Linux audit framework records selected security-relevant events. It provides evidence but does not automatically block an action. 

sudo systemctl status auditd
sudo auditctl -s
sudo auditctl -l

Authentication reports:

sudo ausearch -m USER_LOGIN -ts today
sudo aureport --auth
sudo aureport --failed

Temporary watch rule:

sudo auditctl \
  -w /etc/sudoers \
  -p wa \
  -k sudoers_changes

Search by key:

sudo ausearch -k sudoers_changes

Persistent rules normally belong under /etc/audit/rules.d/.

13. Protect Secrets and Sensitive Files

Find overly broad permissions:

find /path/to/application \
  -type f \
  -perm /o+r \
  -print

Example secret-file permissions:

sudo chown appuser:appgroup /etc/myapp/secret.env
sudo chmod 640 /etc/myapp/secret.env

Important rules:

  • Never store secrets in Git history.
  • Do not pass secrets through command-line arguments.
  • Do not print secrets in application or CI logs.
  • Use a secret manager when available.
  • Rotate credentials after suspected exposure.
  • Separate human credentials from service credentials.

14. Disk and Data Encryption

Inspect block-device filesystems:

lsblk -f
findmnt
sudo blkid

Inspect an existing LUKS device carefully:

sudo cryptsetup luksDump /dev/DEVICE

Security planning must include:

  • Encryption at rest
  • Encryption in transit
  • Secure key storage
  • Recovery-key procedures
  • Encrypted and tested backups
  • Credential and certificate rotation
Incorrect cryptsetup operations can destroy access to data. Practice using disposable lab disks before production use.

15. Kernel and Network Hardening

Inspect important runtime settings:

sysctl kernel.randomize_va_space
sysctl kernel.kptr_restrict
sysctl kernel.dmesg_restrict
sysctl fs.protected_hardlinks
sysctl fs.protected_symlinks
sysctl net.ipv4.conf.all.accept_redirects
sysctl net.ipv4.conf.all.send_redirects
sysctl net.ipv4.conf.all.rp_filter

Persistent custom settings normally go under:

/etc/sysctl.d/*.conf

Validate and load configuration:

sudo sysctl --system
Hardening values are workload-specific. Reverse-path filtering, forwarding and namespace restrictions can break routers, VPNs, containers or Kubernetes nodes. Test first.

16. systemd Service Hardening

Measure a service:

systemd-analyze security SERVICE_NAME.service

Common sandboxing directives:

[Service]
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictSUIDSGID=true
LockPersonality=true

Limit capabilities when required:

CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE

Create an override safely:

sudo systemctl edit SERVICE_NAME.service
sudo systemctl daemon-reload
sudo systemctl restart SERVICE_NAME.service
Add restrictions gradually and test every application feature. Some services legitimately require filesystem, kernel, device or network access.

17. File Integrity and Suspicious Activity

Inspect SUID files:

sudo find / \
  -xdev \
  -type f \
  -perm -4000 \
  -print 2>/dev/null

Inspect recent changes:

sudo find /etc \
  -type f \
  -mtime -1 \
  -print

Review processes and connections:

ps auxf
sudo ss -tulpn
sudo lsof -i
sudo lsof +L1

Distribution package verification:

# RPM-based systems
sudo rpm -Va

# Debian-based systems when debsums is installed
sudo debsums -s
Verification output requires analysis. Configuration changes and package updates can produce legitimate differences.

18. Production Scenario — SSH Login Failure

  1. Do not close the working administrator session.
  2. Validate SSH configuration.
  3. Check service status and logs.
  4. Check firewall and cloud security rules.
  5. Verify user, shell, home and key permissions.
  6. Check SELinux or AppArmor denials.
  7. Test from a second terminal before reloading.
sudo sshd -t
sudo sshd -T
sudo systemctl status ssh sshd
sudo journalctl -u ssh -u sshd --since "30 minutes ago"
sudo ss -ltnp | grep ':22'
getent passwd USERNAME
namei -l /home/USERNAME/.ssh/authorized_keys

19. Production Scenario — Application Permission Denied

  1. Capture the exact error and affected path.
  2. Identify the service account.
  3. Inspect every parent directory.
  4. Check ACLs.
  5. Check SELinux or AppArmor logs.
  6. Apply the smallest necessary permission or policy change.
  7. Retest and document the result.
systemctl show SERVICE_NAME -p User -p Group
namei -l /path/to/file
getfacl /path/to/file
ls -lZ /path/to/file
sudo ausearch -m AVC -ts recent
sudo journalctl -k | grep -i denied

20. Production Scenario — Unexpected Open Port

sudo ss -ltnp
sudo ss -lunp
sudo lsof -i :PORT
ps -fp PID
sudo readlink -f /proc/PID/exe
sudo systemctl status SERVICE_NAME
sudo journalctl _PID=PID
  1. Identify the process and binary.
  2. Determine who started it and why.
  3. Check related service, container and scheduled jobs.
  4. Preserve logs and evidence.
  5. Contain the system according to the incident plan.
  6. Rotate exposed credentials.
  7. Rebuild from trusted sources if compromise is confirmed.
During a suspected compromise, randomly deleting files or killing processes may destroy evidence. Follow the approved incident-response procedure.

🎯 Interview Questions

What is defence in depth?

Multiple independent security controls protect the system so the failure of one control does not expose everything.

DAC vs MAC?

DAC uses ownership and permission decisions controlled by resource owners. MAC adds centrally enforced policy, such as SELinux or AppArmor.

Why avoid direct root login?

Named accounts plus controlled sudo provide accountability, smaller privilege scope and better auditing.

SELinux denial troubleshooting?

Reproduce the problem, inspect AVC logs, confirm labels and booleans, apply the smallest correct policy change, and retest in enforcing mode.

Why use capabilities?

They grant a process a specific privilege instead of the entire root privilege set.

What does auditd provide?

It records selected system and security events for investigation and compliance. It does not itself prevent the event.

First response to a suspected compromise?

Preserve evidence, follow the incident plan, contain affected systems, protect credentials, determine scope and recover from a trusted state.

✅ Production Security Checklist

  • Only required ports are listening.
  • Unused services are disabled.
  • Security updates are applied through a tested process.
  • Direct root SSH login is disabled.
  • SSH keys and MFA are used where possible.
  • Firewall rules use least access.
  • SELinux or AppArmor is enforced.
  • sudo rules grant only required commands.
  • Secrets are protected and rotated.
  • Logs are centralized and monitored.
  • Important changes are audited.
  • Backups are encrypted and restoration is tested.
  • Service accounts cannot log in interactively unless required.
  • Incident-response access and procedures are tested.
