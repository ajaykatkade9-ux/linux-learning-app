🐚 Bash & Shell Scripting

Shell automation for Linux administration, DevOps tasks, health checks, deployments and production troubleshooting.

A good production script should be predictable, readable, fail safely and return useful exit codes.

1. Shebang

#!/usr/bin/env bash

The shebang tells the operating system which interpreter should run the script.

2. Create and Run a Script

cat > hello.sh <<'SCRIPT'
#!/usr/bin/env bash

echo "Hello from Bash"
SCRIPT

chmod +x hello.sh

./hello.sh

3. Variables

NAME="server01"

echo "$NAME"

ENVIRONMENT="production"

echo "Environment: $ENVIRONMENT"

Do not put spaces around = in normal Bash variable assignment.

4. Environment Variables

export APP_ENV="production"

echo "$APP_ENV"

printenv APP_ENV

Child processes can inherit exported environment variables.

5. Script Arguments

$0   Script name
$1   First argument
$2   Second argument
$#   Number of arguments
$@   All arguments
Example: 
#!/usr/bin/env bash

echo "Script: $0"
echo "First argument: $1"
echo "All arguments: $@"

6. Command Substitution

HOSTNAME=$(hostname)

DATE=$(date)

echo "$HOSTNAME"
echo "$DATE"

Command substitution captures command output into a variable.

7. Exit Codes

Linux commands return an exit status. 

0     Success
non-0 Failure or another condition
Check the previous command: 
echo $?
Example: 
grep root /etc/passwd

echo $?

8. if / else

if [ -f /etc/passwd ]; then
  echo "File exists"
else
  echo "File missing"
fi

9. Numeric Comparisons

NUMBER=10

if [ "$NUMBER" -gt 5 ]; then
  echo "Greater than 5"
fi
Common operators: 
-eq  equal
-ne  not equal
-gt  greater than
-ge  greater or equal
-lt  less than
-le  less or equal

10. String Comparisons

ENV="prod"

if [ "$ENV" = "prod" ]; then
  echo "Production"
fi
Check empty variable: 
if [ -z "$ENV" ]; then
  echo "ENV is empty"
fi

11. File Tests

-f   regular file
-d   directory
-e   exists
-r   readable
-w   writable
-x   executable
Example: 
if [ -d /var/log ]; then
  echo "/var/log exists"
fi

12. for Loop

for service in ssh cron nginx; do
  echo "Checking $service"
done

13. while Loop

COUNT=1

while [ "$COUNT" -le 5 ]; do
  echo "$COUNT"
  COUNT=$((COUNT + 1))
done

14. case Statement

ENV="$1"

case "$ENV" in

  dev)
    echo "Development"
    ;;

  prod)
    echo "Production"
    ;;

  *)
    echo "Unknown environment"
    ;;
esac

15. Functions

check_disk() {
  df -h /
}

check_disk
Function with argument: 
say_hello() {
  echo "Hello $1"
}

say_hello "DevOps"

16. Arrays

SERVICES=("ssh" "cron" "docker")

for service in "${SERVICES[@]}"; do
  echo "$service"
done

17. Quoting

Always be careful with variables containing spaces or special characters.

Prefer: 
echo "$VARIABLE"

rm -- "$FILE"
over unquoted variable usage where appropriate.

18. set -euo pipefail

A common defensive pattern: 
set -euo pipefail
Conceptually:
  • -e — exit when an unhandled command fails in applicable contexts
  • -u — error on unset variables
  • pipefail — make pipeline failures easier to detect

These options are useful, but scripts still need thoughtful error handling.

19. Logging

log() {
  echo "$(date '+%Y-%m-%d %H:%M:%S') $*"
}

log "Application check started"

20. Redirect Output

./script.sh > script.log 2>&1
Append instead: 
./script.sh >> script.log 2>&1

21. Health Check Script

#!/usr/bin/env bash

set -u

URL="http://127.0.0.1:8081"

if curl -fsS "$URL" > /dev/null; then
  echo "Application is healthy"
  exit 0
else
  echo "Application health check failed"
  exit 1
fi

22. Disk Usage Check

#!/usr/bin/env bash

THRESHOLD=80

USAGE=$(df -P / | awk 'NR==2 {gsub("%","",$5); print $5}')

if [ "$USAGE" -ge "$THRESHOLD" ]; then
  echo "WARNING: Disk usage is ${USAGE}%"
  exit 1
else
  echo "Disk usage is ${USAGE}%"
fi

23. Service Check

#!/usr/bin/env bash

SERVICE="$1"

if systemctl is-active --quiet "$SERVICE"; then
  echo "$SERVICE is running"
  exit 0
else
  echo "$SERVICE is not running"
  exit 1
fi

24. Validate Required Arguments

if [ "$#" -ne 1 ]; then
  echo "Usage: $0 SERVICE_NAME"
  exit 2
fi

25. trap

trap can run cleanup logic when the script receives certain signals or exits. 

TMPFILE=$(mktemp)

cleanup() {
  rm -f "$TMPFILE"
}

trap cleanup EXIT

26. Debugging Bash

Syntax check: 
bash -n script.sh
Trace execution: 
bash -x script.sh
Enable tracing inside a script: 
set -x

27. ShellCheck Concept

ShellCheck is a static-analysis tool commonly used to find potential shell-script problems.

If installed: 
shellcheck script.sh

This is especially useful before using automation scripts in CI/CD.

🔥 Production Scenario 1 — Works Manually, Fails in Cron

Common differences:

  • PATH
  • Environment variables
  • Working directory
  • Runtime user
  • Permissions
Investigate: 
env

echo "$PATH"

pwd

whoami

Use absolute paths where appropriate and explicitly define required environment.

🔥 Production Scenario 2 — Script Continues After Failure

A deployment script runs multiple commands but continues even after one important command fails.

Better pattern: 
#!/usr/bin/env bash

set -euo pipefail

Also explicitly check critical operations and return meaningful exit codes.

🔥 Production Scenario 3 — Variable Is Empty

A script deploys to the wrong environment because an expected variable was missing.

Check: 
: "${APP_ENV:?APP_ENV must be set}"

This forces the script to stop if the variable is missing or empty.

🔥 Production Scenario 4 — Pipeline Hides Failure

Example: 
COMMAND1 | COMMAND2
Without proper handling, a failure in COMMAND1 can be missed. Use: 
set -o pipefail
Then inspect: 
echo $?

🔥 Production Scenario 5 — Script Deletes Wrong Path

Production automation should validate dangerous variables before file operations.

Safer thinking: 
if [ -z "${TARGET_DIR:-}" ]; then
  echo "TARGET_DIR is empty"
  exit 1
fi

Never build automation that performs destructive operations without validation and clear safeguards.

🔥 Production Scenario 6 — Health Check Fails

curl -v http://127.0.0.1:PORT

ss -ltnp

systemctl status SERVICE_NAME

journalctl -u SERVICE_NAME

Determine whether the failure is the script, application, network endpoint or dependency.

echo

echo

🧪 Argument Lab

cat > usercheck.sh <<'SCRIPT'
#!/usr/bin/env bash

if [ "$#" -ne 1 ]; then
  echo "Usage: $0 USERNAME"
  exit 2
fi

USER_NAME="$1"

if id "$USER_NAME" > /dev/null 2>&1; then
  echo "User exists: $USER_NAME"
  exit 0
else
  echo "User does not exist: $USER_NAME"
  exit 1
fi
SCRIPT

chmod +x usercheck.sh

./usercheck.sh root

🧩 Quick Recall

What does $? contain?

The exit status of the most recently completed foreground pipeline or command context. Zero normally means success.

Why quote "$VARIABLE"?

Quoting helps preserve the variable as a single value and avoids many word-splitting and pathname-expansion surprises.

Script works manually but not from cron. What do you check?

PATH
environment variables
working directory
runtime user
permissions
absolute command paths
logs

🗣️ Strong Interview Answer

“When I write Bash automation, I keep inputs explicit, quote variables, validate required arguments and environment variables, return meaningful exit codes and log important actions. For critical scripts I use defensive error handling such as set -u and pipefail where appropriate, test the script with bash -n and tracing, and avoid assuming that cron, CI/CD or systemd has the same environment as my interactive shell.”
